# ADR 001: Переход от изолированных буферов компонентов к Canvas API и SubCanvas

* **Статус:** Принято
* **Ветка реализации:** `feat/issue-16-add-canvas-api`
* **Контекст задачи:** Оптимизация подсистемы рендеринга и управления памятью в движке

---

## 1. Контекст и проблематика
На раннем этапе архитектура движка предполагала, что каждый визуальный компонент (`Component`) инкапсулирует собственный независимый буфер ячеек (`Buffer`), выделяемый в динамической памяти при создании или изменении размера виджета.

В процессе работы такой подход выявил критические архитектурные недостатки:
1. **Избыточные аллокации и нагрузка:** отрисовка иерархии дерева компонентов требовала поэлементного копирования (blitting) массивов ячеек из дочерних буферов в родительские контейнеры, а затем в экранный буфер, создавая миллионы временных объектов в памяти.
2. **Сложность отсечения:** если дочерний элемент выходил за границы родителя, логика обрезки требовала сложного пересчета границ каждого локального буфера.

Встала задача устранить множественное копирование памяти и упростить координатную сетку для компонентов.

---

## 2. Рассмотренные альтернативы
* **Альтернатива 1 (Глобальные абсолютные координаты):** Компоненты рисуют прямо в глобальный буфер по абсолютным экранным координатам `(X, Y)`.
    * *Минусы:* Ломается изоляция виджетов. Каждый виджет должен знать абсолютное смещение своего родителя на экране; невозможно легко переносить контейнеры без ручного пересчета всех дочерних координат.
* **Альтернатива 2 (Canvas API с SubCanvas):** Единый экранный буфер в связке с легковесной структурой-проекцией `Canvas`.

---

## 3. Принятое решение
Принято решение перейти на **архитектуру Canvas API с иерархическими SubCanvas**.

Вся графическая подсистема переведена на работу с единым корневым буфером:
1. Создается единственная матрица ячеек `Buffer` на все приложение (теневой экранный буфер).
2. Компонентам передается легковесная структура `Canvas`, содержащая:
    * указатель на целевой `*Buffer`;
    * смещения координат относительно экрана `offsetX`, `offsetY`;
    * прямоугольное окно отсечения `clipW`, `clipH`.
3. Контейнеры порождают дочерние холсты вызовом `canvas.SubCanvas(x, y, w, h)`, который не аллоцирует новую память под пиксели, а лишь сужает окно видимости и корректирует локальные смещения.
4. Примитивы рисования (`SetCell`, `DrawRect`, `DrawString`) транслируют локальные координаты `(x, y)` в абсолютные и проверяют попадание в `clip-box`.

---

## 4. Последствия (Trade-offs)

### Положительные:
* **Zero-allocation рендеринг:** отрисовка всего дерева интерфейса больше не выделяет динамическую память под пиксели, что полностью устранило паузы сборщика мусора (GC Pauses).
* **Автоматическое отсечение (Clipping):** дочерний виджет физически не может нарисовать символ за пределами отведенной ему родителем области.
* **Локальные координаты:** разработчик виджета всегда оперирует локальной системой координат `(0, 0)` относительно верхнего левого угла своего компонента.
* **Снижение потребления RAM:** оперативная память расходуется только на одну матрицу терминала вместо десятков буферов для каждого виджета.

### Отрицательные:
* **Связанность с Canvas:** компоненты потеряли возможность автономной отрисовки без наличия контекста `Canvas`.
* **Трансляция координат:** каждая операция записи ячейки выполняет проверку условий границ клиппинга и сложение смещений (однако эти операции процессора на порядки дешевле операций аллокации памяти).
